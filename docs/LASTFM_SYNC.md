# Last.fm syncing and reviewed album-name coverage

This is the persistent **sync-only pilot**, separate from the frozen [feasibility study](LASTFM_LISTENING_STUDY.md). It collects future scrobbles and resolves reviewed album identities. It does not count completed albums, create diary entries, publish catalog albums, or change manual listens. The later counting scope remains in [AUTOMATIC_ALBUM_LISTENS.md](AUTOMATIC_ALBUM_LISTENS.md).

## Account and privacy contracts

The Last.fm pilot section, including detected listen sessions, is the owner-only **Last.fm** tab on the signed-in user's profile (`/account`). Start authorization while signed into Rescened, authorize the application at Last.fm, and return to `/account/lastfm/callback`, which sends the browser back to that tab. The server binds an expiring, single-use attempt to the authenticated Clerk user, exchanges the token, and uses the provider-returned account name. The browser removes callback parameters from its URL; the server stores only a hash of the attempt state. Session keys and authorization tokens are not persisted.

A Last.fm account can have only one active or paused connection, and a Rescened user can have only one connection. Another user cannot take over an existing connection. Pause closes the activation window; resume begins another. Reconnection starts from the new connection time. Paused-period listening and history before connection are excluded.

Last.fm's recent-track endpoint is public. Revoking authorization at Last.fm does not reliably stop those reads. Users must use Rescened's pause or disconnect controls. Disconnect fences in-flight jobs and schedules private evidence cleanup. Signed Clerk `user.deleted` events and owner-existence checks provide account-deletion cleanup. The webhook runs one transaction (`lib/accountDeletion.js` plus the listening cleanup) that deletes auth attempts, automatic-listen receipts and fences, diary entries and their `ListenCreation` receipts, boards with their saved albums and listen memberships, the user's likes and track rankings, follows in both directions, notifications the user sent or received, and the profile. The same transaction deletes the user's Last.fm connection, including the username, with its scrobbles, detections, and detection evidence. It also clears connection references from queued jobs. Account deletion therefore does not wait for the worker. Disconnect still relies on the worker's cleanup job. Reviews stay public but are anonymized: their author becomes a server-only placeholder that API responses show as `userId: null` and "deleted user", that resolves to no profile or review list, and that receives no notifications. Their private idempotency key is cleared, and other users' likes on them remain. Album submissions and moderation history are append-only and are kept unchanged. Without transaction-capable MongoDB, the webhook returns `503 CLEANUP_UNAVAILABLE` and changes nothing, so Clerk retries delivery.

Normalized scrobbles retain exact timestamps only in owner-private records for at most 30 days from playback. Reads enforce expiration as well as MongoDB TTL deletion, since TTL deletion is asynchronous. Production does not retain complete raw provider responses. Moderator cases retain reusable artist/album metadata, source evidence, encounter totals, and a distinct-listener count, without usernames, listening sequences, or exact listening timestamps. Case and decision dates are review provenance, not playback dates.

`LASTFM_TIMEOUT_MS`, `LASTFM_RETRIES`, and `LASTFM_REQUESTS_PER_MINUTE` tune bounded provider behavior. Keep these server-side; never place credentials or allowlists in Vite variables. Provider calls are opt-in runtime behavior, not part of normal tests.

Before enabling any pilot user:

1. Confirm Last.fm application name, description, callback registration, attribution and data-use requirements against its [web authentication documentation](https://www.last.fm/api/webauth), [recent-track documentation](https://www.last.fm/api/show/user.getRecentTracks), and [API terms](https://www.last.fm/api/tos). Commercial/research use requires the provider's stated contact process. This repository does not establish permission for a particular deployment.
2. Provision transaction-capable MongoDB, application credentials, and a verified Clerk webhook destination at `/webhooks/clerk/listening`. The webhook route verifies the original raw bytes before JSON parsing. Do not log webhook bodies or callback request query strings in reverse proxies, analytics, error reporting, or access logs. Serve the callback with `Referrer-Policy: no-referrer` and `Cache-Control: no-store` at the frontend host.
3. Set a small explicit pilot allowlist. Initialize application indexes and start one supervised worker. No worker runs inside an API process.
4. Validate signed-in connect, status, pause/resume, disconnect, webhook delivery, throttling and retained-event resolution in the named pilot environment. Live provider verification and deployment are separate operator steps; repository tests use synthetic providers and temporary databases.

Provide environment variables through the deployment environment or an external credentials file. The worker and operator commands do not implicitly load the repository `.env`. For local development only, `npm run listening:worker:dev` starts the worker with the root `.env`. On startup failure the worker prints only an error code or class name, such as `MONGO_URI_REQUIRED` or `MongoServerSelectionError`. After startup, a failed pass (for example a MongoDB failover) is logged as `Listening worker pass failed: <code> (attempt N, retrying in Ns)`. The worker then retries with exponential backoff from 5 seconds up to 5 minutes, and resets after the next successful pass. Unfinished jobs keep their lease and are retaken when it expires. The due-sync, sweep, detection-expiry, stale-mapping and catalog-rediscovery scans run at most once a minute. Connect and resume enqueue their own first sync. SIGINT and SIGTERM stop the worker promptly, even during a backoff.

```sh
npm run listening:worker
npm run listening:metrics -- --environment pilot
```

Keep the worker running for disconnect cleanup even when reads are disabled. Account-deletion cleanup does not need it. Supervise restarts: startup failures still exit with code 1. Alert on repeated `pass failed` lines. Do not infer successful ingestion from a running process alone.

## Sync and resolution behavior

When `LASTFM_DISCOVERY_ENABLED=true`, the worker also watches for catalog albums from any publish path, such as community approval or a catalog import. A pending or `no_catalog_match` case matches when the artist matches the album's display or credited artist, and the title matches exactly or after removing an edition label like "(Deluxe Edition)". Moderator `no_catalog_match` decisions are eligible because publication can resolve the missing album; explicit `rejected` and `approved` cases are excluded. A queued catalog job rechecks eligibility when it executes, and the case revision fences moderator decisions made while discovery runs. Suggestions still require moderator approval.

Each observed case/album pair has a unique durable discovery job. Overlapping scans and worker restarts cannot enqueue the pair twice, and another discovery cannot falsely acknowledge a publication it did not see. Existing completed jobs are left untouched. Failed or incomplete catalog discoveries retry at hourly intervals, up to three retries after the initial attempt; case revision conflicts can also retry within that budget. Exhausted jobs remain visible in `catalogRediscoveryJobs.failed` in the queue report, and the case keeps its discovery error. A moderator refresh is the explicit recovery path after the retry budget, or after reopening a case whose catalog job was skipped because it had already been approved or rejected; another catalog album creates its own observation job.

A leased database checkpoint persists independent recent/full scan cursors across worker restarts. Scans resume by immutable album and case IDs, one credited artist at a time. Each pass examines at most 10 album pages and 200 cases, with case pages of 25, and creates at most 25 jobs. At most 100 catalog jobs may be pending or running; scanning pauses at that limit until work finishes. The 25-case page is not a lifetime cap: later cases are visited on later passes. New jobs are spaced 15 seconds apart and queued at most five minutes ahead. Retries keep their own hourly schedule. Recent scans start with a seven-day lookback and overlap by 15 minutes. They alternate with a bounded full-catalog sweep, repeated daily after completion, so albums with old preallocated IDs or late commits are eventually observed without holding up recent scans. Very large backlogs take multiple passes; a restart resumes the saved cursors and safely replays any uncheckpointed inserts using the durable job keys. On first rollout, eligible names can rerun once for each matching catalog album as the initial sweeps progress.

Mapping queue listener counts are refreshed when new unresolved evidence arrives and exclude evidence expired at that worker pass, even before MongoDB TTL cleanup. They are stored counts, not a live census. Before enabling this release against an existing pilot database, reconcile cases created before `listenerCount` existed; absent counts display as zero and can affect queue ordering. The new production worker does not perform an automatic data backfill.

Active connections are due approximately every five minutes, subject to provider budget and capacity. Each job captures fixed `from`/`to` bounds and paginates the complete window, using a 48-hour overlap for delayed scrobbles. Job progress survives restart; completed cursors never skip unprocessed pages. Now-playing rows are excluded, and repeated pages/retries do not create duplicate events or inflate encounter counts. A same-second identical artist/album/track event is conservatively treated as one event. A repeated delivery that disagrees on a populated MusicBrainz identifier keeps the first values and records each disagreeing field in `identityConflictFields`. Only a disagreeing `trackMbid` marks the event `identityConflict`, which detection does not count. Album and artist IDs do not decide the album (the reviewed text mapping does), and Last.fm often switches them between releases of the same album, so those disagreements are recorded for diagnosis but the event still counts. The detector applies the same rule to duplicates within one evaluation.

Catch-up stops at the 30-day retention boundary and exposes older gaps. Regular sync refetches only a 48-hour overlap. When `LASTFM_DEEP_SWEEP_ENABLED=true`, each active pilot connection also gets a daily sweep job that refetches from the later of 14 days ago and `connectedAt` up to `completedThrough`. It picks up offline or late-uploaded scrobbles, never moves the cursor, records `lastSweepAt`, and runs only when no other job is due. Without the sweep, events delayed beyond the overlap may be missed. The sweep shares the global `lastfm` request budget. If `lastfm_request_budget_exhausted` or `lastfm_rate_limited` errors, cooldowns, or regular-sync lag increase, investigate the sweep first; see [automatic album listens](AUTOMATIC_ALBUM_LISTENS.md). Provider pagination changing during a fetch leaves the window incomplete rather than silently advancing it. Revision and lease fences prevent paused, disconnected, replaced, or expired work from committing. Provider outages leave the normal catalog and manual diary usable.

Only an exact approved normalized provider/track-artist/album-label key resolves at runtime. Normalization applies Unicode NFKC, case folding, trimming and whitespace collapsing; it preserves punctuation and edition qualifiers. Artist names from recent tracks are not assumed to be album artists. Guest-credit variations remain unresolved unless separately reviewed.

A mapping establishes identity to an existing public Rescened `albumId`. It does **not** certify a standard tracklist. `baselineAvailable` requires a current moderator-reviewed MusicBrainz standard baseline; nonempty catalog tracks alone cannot change this. See [baseline review and enrichment](TRACKLIST_BASELINES.md). Standard-baseline counting and its 80% rule remain unimplemented.

## Discovery and moderation

Unresolved names share one case per exact normalized key. The moderator queue ranks cases by distinct listeners first, then encounters, so an album many users play outranks one user's repeat plays. Each new unresolved event recounts the distinct connections holding retained unresolved events for that key; the case stores only that count, never user or connection identifiers, and the count is refreshed only when a new event arrives. Listener and encounter counts affect priority only. Repeated ingestion of the same retained event does not increase that count. Rejected cases remain rejected on subsequent encounters; a moderator refresh or genuinely changed complete provider evidence is required to reopen them.

Discovery first searches the local catalog, including exact title-only candidates under different artist credits. Such differences are shown for review and never create global artist aliases. It may suggest up to five existing albums from exact names, verified MusicBrainz release-to-release-group relationships, or conservative edition-label simplification with track comparison. Search hits are labeled as candidates, not verified release relationships. Trailing deluxe, expanded, bonus-track and anniversary labels may be simplified only for discovery. Live, remix, acoustic, instrumental and re-recorded distinctions remain intact.

Evidence includes provider links and retrieval dates, track counts, shared/missing/extra tracks, duplicate-title ambiguity and identifier conflicts. Track comparisons identify whether they use a reviewed standard baseline or unreviewed catalog tracks. Track overlap is not an approval signal by itself. Provider errors leave discovery incomplete. Query and candidate caps are recorded separately on the `candidate_discovery` evidence (`candidatesFound`, `candidatesShown`, `candidateLimitReached`, and `candidateQueryLimitReached` when a local query or the bounded MusicBrainz search result was full, regardless of hit relevance), because an incomplete run keeps the previous candidate snapshot. The workspace warns when search limits were reached, including when no local candidates were found, when candidates were cut or when the last refresh was incomplete and the shown candidates come from an earlier discovery. A complete search with no suitable local result may mark `no_catalog_match`; the moderator can use the existing catalog-submission workflow, which remains a separate publication process.

The mapping workspace is `/moderation/album-mappings`, beside album-submission moderation. Existing moderators can filter the queue, inspect evidence, select another existing catalog album, approve, reject, mark no match, refresh or revoke. Expected revisions are mandatory. Reasons are optional (at most 2,000 characters); a blank one records a standard note for the action, such as "Approved by a moderator." Approval/revocation updates the mapping, case and append-only audit in one transaction; stale commands return 409 and unavailable transactions return 503. Case candidates are a discovery snapshot, but queue and detail reads report each candidate's current `catalogRevision`. A baseline confirmation that fills an album's empty tracks advances that revision, so a mapping reviewed after it approves against the new revision; an approval that still sends the older one returns `CATALOG_REVISION_CONFLICT`.

An approved mapping pins the catalog revision it was reviewed against. A later catalog change leaves it active but stale: the worker and owner reads resolve its events as `unavailable`, and detections are held for `stale_mapping` until a moderator acts. Two changes do not change identity, so they move the mapping to the new revision without review. A baseline confirmation that fills empty tracks does this inside its transaction. A cover backfill write does it right afterwards, in a transaction that also carries the reviewed tracklist baseline forward ([tracklist baselines](TRACKLIST_BASELINES.md)) and queues reprocessing. If that transaction fails, the cover stays committed and the report records `revisionCarryFailed`, which leaves the mapping and baseline stale. Corrections, importer refreshes, and deletions still require review. The queue marks such cases with `mappingStale`, and `GET /moderation/album-mappings?stale=true` lists only them (any other `stale` value returns `INVALID_STALE`). Detail responses add `mapping.currentCatalogRevision` (`null` if the album is gone) and `mapping.stale`. `POST /moderation/album-mappings/:caseId/reconfirm` accepts `{ expectedRevision, expectedCatalogRevision, reason }` for an approved case. It keeps the same album, sets the mapping to the current catalog revision, bumps the mapping and case revisions, appends a `reconfirmed` audit entry, and queues reprocessing, all in one transaction. It returns `CATALOG_REVISION_CONFLICT` when the album moved past the revision the moderator reviewed, `MAPPING_NOT_STALE` when nothing changed, `MAPPING_NOT_ACTIVE` when there is no active mapping, and `CATALOG_ALBUM_NOT_FOUND` when the album was deleted (revoke instead). To point the name at a different album, revoke the mapping and approve again.

Approvals queue retained-event reprocessing for active connections only. Revocation and changed catalog revisions invalidate cached resolution and schedule reevaluation. Owner event reads also check current mapping/catalog validity, so stale cached matches do not remain authoritative while a worker catches up. With `LISTENING_DETECTION_ENABLED=true`, pilot owners can save an IANA time zone (`PUT /connections/lastfm/time-zone`) and read their private detected sessions (`GET /connections/lastfm/detections`); see [automatic album listens](AUTOMATIC_ALBUM_LISTENS.md). Reviewed mappings are separate from `AlbumCatalog`; discovery and moderation never create catalog albums.

## Reviewed seed workflow

Study IDs and `data/listening-study/album-name-mappings.json` are not production identities. There is no automatic import. An operator must independently bind each reusable artist/album name to an existing public UUID-v4 `albumId`.

Prepare a JSON array containing only `artist`, `album`, `albumId`, `reason`, and `sources` (HTTPS source URL strings). Do not include usernames, tokens or listening evidence. A dry-run performs catalog reads, requires existing targets, captures catalog/case revisions, and refuses already mapped keys. As in the catalog importer, a catalog album with no stored `catalogRevision` is treated as revision 1 by seeds, the worker, and owner reads. It does not modify the database or overwrite an existing output file.

```sh
npm run listening:mapping-seeds -- --dry-run \
  --environment pilot --bindings /private/path/bindings.json \
  --output /private/path/mapping-plan.json
```

Review the exact plan and printed SHA-256. Applying requires explicit authorization for that named environment, the same target fingerprint, the reviewed file, and its checksum:

```sh
npm run listening:mapping-seeds -- --apply \
  --environment pilot --confirm-environment pilot \
  --plan /private/path/mapping-plan.json --sha256 REVIEWED_SHA256 \
  --reviewer REVIEWER_ID
```

The apply rechecks all target/case revisions and creates mappings, audit records and reprocessing jobs transactionally. Any conflict rolls back the batch. Keep the plan, checksum and command result as the review record. No seed apply or production database access was performed during implementation.

## Monitoring and verification

`listening:metrics` emits aggregates, not individual names or listening histories. Review sync lag, incomplete windows, deferred jobs/provider errors, unresolved observed names, queue age, revoked mappings, baseline-ready and baseline-unavailable names, and `baselineReviews` status counts ([details](TRACKLIST_BASELINES.md#validation-and-operations)). The coverage denominator is **distinct eligible names observed in retained evidence for active connections**. Its numerator requires an active reviewed mapping with a current existing catalog target. An empty denominator is reported as null coverage.

`listening:queue-report -- --environment NAME [--days N]` is a read-only aggregate report on the mapping and tracklist review queues, for sizing [automated assistance](AI_ASSISTED_MAPPING_PLAN.md#build-order). It prints counts and durations only, with no names, album, release or reviewer IDs. The window defaults to 30 days, and the maximum is 365.

- `mappingQueue` describes pending cases by stored candidates. It counts cases with none, one or several candidates, a verified top candidate, a top candidate with identifier conflicts, and a single clean verified candidate. It also counts cases with an edition-labelled name (for example "Deluxe Edition"), cases whose candidate list hit a cap, and cases whose last discovery failed or was incomplete. Ages are seconds since the case was created, so a case reopened by a revoke or new evidence reports its original age.
- `noCatalogMatch` counts cases the worker or a moderator closed as having no catalog album, with their listeners and how many have an edition-labelled name. The worker closes these without an audit, so they are read by status rather than by window. Edition-labelled cases here are the missing edition entries.
- `catalogRediscoveryJobs` counts pending, running, completed and terminally failed catalog discovery jobs, without identifiers. Terminal failures need a moderator refresh after the underlying problem is resolved.
- `mappingDecisions` counts moderator decisions in the window; `seededApprovals` counts mapping-seed applies. Worker status changes write no audit and are not counted. `firstDecisionSeconds` times only a case's first decision, so cases decided again after a revoke or seed are not timed. `approvals` compares the approved album with the case's stored candidates. Those candidates come from the last discovery, which a later refresh can replace. `approvalCandidateBasis: "latest_stored_discovery"` makes that limitation explicit; these are current-snapshot comparisons, not historical decision-quality measurements.
- `baselineDecisions` counts tracklist commands by target kind. `queued` covers album decisions that followed an enrichment queue entry. Only the first decision after each queue entry counts. It shows whether moderators confirmed the queued release, confirmed a different one, or deferred, and how long that took. Albums never queued by enrichment have no stored recommendation, so they are not included. `replace` changes an already reviewed tracklist; it is not a rejected recommendation.
- `baselineQueue` repeats the `baselineReviews` status counts from `listening:metrics`.

The report scans audit collections by date without an index, so run it against a replica or off-peak. It needs a database URI the operator names and never writes.

```sh
npm run listening:queue-report -- --environment pilot --days 30
```

`listening:measurement` is the read-only snapshot collector for the [deterministic mapping metrics plan](DETERMINISTIC_MAPPING_METRICS_PLAN.md). It reads a versioned exposure manifest (schema 3) and prints aggregates only. Measurement is prospective only. There is no historical deploy or flag reconstruction. The descriptive "before" picture is [the November 1 queue metrics](QUEUE_METRICS_2026-11-01.md), which every report cites as a snapshot, not a control group. Print a blank manifest with `--template`, then check it offline with `--validate-only`. Validation rejects unknown fields and connection strings. Measurement starts when the measurement code is merged and deployed. Every flag below defaults off, so no records exist until the operator turns one on. After deploying the merged code and turning on an exposure's flag, record that time as the exposure's `activatedAt`. Record these facts as they happen, never retroactively:

- `exposures.observations`: when a worker running the merged code began running with `LASTFM_DISCOVERY_ENABLED=true` (slice 2).
- `exposures.reviewEpisodes`: when the deployed API began running with `REVIEW_EPISODES_ENABLED=true` (slice 3).
- `exposures.effortTimer`: when the deployed API and frontend began running with `REVIEW_EFFORT_TIMER_ENABLED=true`.

Each exposure takes `activatedAt`, an optional `deployedRevision`, a `rollbackAt`, and a `verification` note saying how the time was recorded. Append each later flag change to `flagChanges` (`flag`, `enabled`, `at`, optional `note`). Only the study's known flags are accepted, and a change to an exposure's own flag must come after that exposure's `activatedAt`. Also append each pilot allowlist change to `allowlistChanges` (`change`: added, removed or replaced; `count`; `at`). Reports echo changes without their notes. An unrecorded activation leaves that exposure's windowed sections uncollected. The study windows were confirmed on November 1, 2026 and are frozen: a 14-day intake from activation, 7 days of follow-up and one snapshot per day at 06:00 UTC. The template carries them, and validation rejects any other value. The manifest's `environment` is a label: verify the database `MONGO_URI` selects separately, without printing it.

```sh
npm run --silent listening:measurement -- --template > ~/rescened-ops/measurement/manifest.json
npm run --silent listening:measurement -- --manifest ~/rescened-ops/measurement/manifest.json --validate-only
npm run --silent listening:measurement -- --manifest ~/rescened-ops/measurement/manifest.json
```

- `mappingEvidence` is a case-level snapshot of pending mapping evidence. Cases whose discovery predates coverage fields count as unknown coverage, not complete. Problem reasons (provider incompleteness, other failures, candidates retained after a failed refresh, query or candidate caps, candidates bound to an old catalog revision) overlap and are not summed.
- `demandReadiness` uses the `listening:metrics` name denominator, then partitions the distinct catalog albums those mapped names reach into ready pending, unprepared pending, reviewed, stale, deferred, revoked and unknown. Every partition prints its total and whether it reconciles.
- `rediscoveryCensus` traverses the whole catalog to list every case/album pair the versioned rediscovery matcher accepts now, then classifies each pair's catalog job (not enqueued, queued, retrying, running, done without error, terminal error) and whether the album is already a usable candidate. `doneWithoutError` includes safe skips. Catalog jobs whose pair left the cohort are counted by exit reason.
- `rediscoveryOutcomes` follows pairs the scanner newly observed during the intake for 7 days each: candidate gain (pairs and distinct cases) with its attribution (first gained by the pair's own catalog job, by its own job when the album was already present, or by another trigger), the outcome partition at the end of follow-up, terminal-error incidence, retry load and delay percentiles. A run counts toward follow-up by when it was written, which is the commit time for committed runs. Pairs already holding a usable candidate when observed are excluded from gain. Pairs without a full follow-up by the snapshot are censored, not failures. `unrecordedExecution` counts pair jobs that were leased but have no attempt record. Windowed sections are not collected when their records are incomplete or expired. For the observation sections, that means the exposure rolled back before follow-up ended. For the review-episode and effort sections, which need no follow-up, it means a rollback during the intake. Sections are also not collected when the intake is older than the records' retention.
- `discoveryRuns` partitions every discovery run that started in the intake (complete result, incomplete result, failure without result, revision conflict), by trigger, with coverage-field availability and overlapping cap and incompleteness reasons. Skips are counted separately.
- `reviewEpisodes` measures decision-time provenance for mapping (approve, reject, no catalog match) and baseline (confirm, replace, defer, revoke) decisions committed in the intake, against the audit log, which records every decision. Per kind it prints `decisions`, the episode partition (`recorded`, `failed`, `missingUnknown`), `failedByReason` (`capture_failed`, `capture_invalid`, `write_failed`, with `write_timeout` retained for older markers), `episodeCoverage`, coverage and recommendation-run availability among recorded episodes, and how selections relate to the displayed candidates or the recommendation. Decisions inside an interval when `flagChanges` records `REVIEW_EPISODES_ENABLED` off are counted separately as `decisionsWhileFlagOff`. A missing episode with no failure marker stays `missingUnknown`. Causes include a crash between commit and write, a timed-out write whose outcome is still unknown, and episodes removed by `review:clear-episodes`.
- `recommendationRuns` partitions baseline recommender executions in the intake (recommended, no candidate, failed) with overlapping browse, hydration, uninspected-competitor, ambiguity and ordered-difference reasons, and the share later linked to a decision. A decision that differs from the recommendation is disagreement, not an error.
- `reviewEffort` totals opt-in timings in the effort-timer intake: decided and linked to the moderator's own decision, decided without a linked decision, and abandoned. It reports active minutes and percentiles per timing, by kind. It shows totals only, with no per-moderator breakdown and no record IDs. Small groups are not hidden. Totals pool every opted-in moderator, so with one moderator they describe that moderator's own effort.
- `adjudication` appears when `--adjudication DIR` names a completed packet directory (below); otherwise it is `collected: false`.
- Enqueue reach is not measurable, because a pair enters when the scanner observes and enqueues it; the census's `notEnqueued` count shows scan lag.

With `REVIEW_EPISODES_ENABLED=true`, the API keeps a private `ReviewEpisode` per final moderator decision and a `BaselineRecommendationRun` per baseline recommendation (offset 0 of the candidates endpoint). The candidates response returns a `recommendationRunId`; later browse-page responses return page IDs attached to that run. The moderator page passes those IDs with its decision, so the episode records the recommendation and pages actually shown. A missing run or page is recorded as missing provenance rather than replaced with another moderator's run. Mapping snapshots retain the discovery list in display order and rank the selection against that whole list. The evidence is read before the decision's transaction, with each read limited to 1 second. The episode is written after commit, keyed by the audit ID with an idempotent upsert. Capture or write failure never changes the decision response. A confirmed write failure gets a background marker; a write still pending after the 2-second response limit is logged as `write_timeout` and remains unknown until it settles. Episodes store a pseudonymous moderator hash, no reason text, and expire after 180 days. Recommendation runs and their browse pages are best effort and expire after 90 days. The server builds review-observation indexes before accepting requests whenever either recording flag is enabled.

With `REVIEW_EFFORT_TIMER_ENABLED=true`, mapping review and the standalone baseline page show an opt-in timer to moderators. Nothing is timed until a moderator opts in (stored server-side as a hash) and presses Start. Saving a mapping approve, reject or no-match decision, or any baseline decision, ends the timing. Moving to another target, leaving the review page or pressing "Stop without deciding" records it as abandoned. Closing or reloading the tab records nothing. A baseline panel embedded in mapping review uses the mapping page's timer. `GET /moderation/review-effort` returns `{ enabled, optedIn }`. `PUT /moderation/review-effort/opt-in` takes `{ optedIn }`. `POST /moderation/review-effort` takes `{ effortId, kind, targetKind, targetId, targetRevision, outcome, intervals }` and is idempotent on `effortId`. Intervals must be ordered, non-overlapping, at most 4 hours each, within 12 hours overall, and no later than now plus one minute. The server links a decided timing to the moderator's own decision on that target within 10 minutes of its last interval. Each decision links to at most one timing. Timings expire after 90 days. Errors use `REVIEW_EFFORT_TIMER_DISABLED` (503, checked before the rate limit), `REVIEW_EFFORT_OPT_IN_REQUIRED` (403), `INVALID_REVIEW_EFFORT_REQUEST` or `INVALID_REVIEW_EFFORT_INTERVALS` (400) and `REVIEW_EFFORT_CONFLICT` (409).

`review:adjudication` exports a blinded sample for independent checking, read-only. It samples recorded episodes from the review-episode intake that are at least 7 days old and have a comparable choice (mapping approve, reject or no match; baseline confirm or replace), 30 by default with a seed you record. It writes `packet.json`: the evidence and lettered options in random order, with no decision, recommendation, reason or moderator. Every option in an item is described from the same source: catalog album fields for mappings, a bare MusicBrainz release link for baselines. It also writes `key.json` (the moderator's choice per item) and `labels.json`, all into a new, empty directory outside the repository with owner-only permissions, and prints counts and the packet checksum. The adjudicator answers each item in `labels.json` with a letter, `no_match`, `other_match` for an unlisted catalog album, or `insufficient`, and sets `adjudicator` to `independent` or `same_moderator`. For mapping `no_match` or `other_match`, fill that item's `catalogEvidence` with independently checked local-catalog search queries and `matchedAlbumId` (null for no match, the public album ID for an unlisted match). A no-match answer without that evidence counts as insufficient. A rejected case cannot be supported by a no-match answer alone because rejection and catalog absence are different decisions. The report labels same-moderator checks `delayed_self_review`. `listening:measurement --adjudication DIR` verifies that all three files share the packet checksum, then reports supported, unsupported, insufficient and unreviewed counts. The unsupported rate excludes insufficient and unreviewed items.

```sh
npm run --silent review:adjudication -- --manifest ~/rescened-ops/measurement/manifest.json --out ~/rescened-ops/adjudication/2026-11-24 --seed 2026-11-24
npm run --silent listening:measurement -- --manifest ~/rescened-ops/measurement/manifest.json --adjudication ~/rescened-ops/adjudication/2026-11-24
```

`review:clear-episodes` clears `ReviewEpisode` records without touching audit history or any other collection. It is dry-run first. A dry run prints the database name, a cutoff (now, or a past `--cutoff`) and how many episodes recorded at or before the cutoff it would remove. Applying needs that exact cutoff, `--confirm-count` equal to the dry run's count and the connected database's name, plus explicit authorization for each environment. It refuses a future cutoff and a count that changed. Cleared decisions then count as `missingUnknown`, so clear outside a measured intake or note the clear with the report.

```sh
npm run --silent review:clear-episodes
npm run --silent review:clear-episodes -- --apply --cutoff 2026-11-24T06:00:00.000Z --confirm-count 12 --confirm-database rescened_dev
```

With discovery enabled, the worker writes a private `ListeningDiscoveryAttempt` record for every discovery job execution: its trigger, outcome or skip reason, provider completeness, caps, the candidates before and after, and whether the observed pair's album was present. A committed run's record is validated before its transaction and written inside it with the commit time, so recording can never block discovery. Skip, failure, conflict and lease-loss records are best effort and never change the job. Records hold no user IDs, are never serialized by an API and expire after 90 days. Each new catalog job's payload also records when the scanner observed the pair, whether the album was already a usable candidate, and `eligibleAfter`: the start of the last full sweep to complete before that observation, which is a lower bound on when the pair became eligible. It is `null` until a full sweep completes on a worker with this change, and an album checkpointed mid-scan before the change gets no observation. Publication commit times are never inferred from IDs.

The collector reads projected pages of 500 records, at most 10,000 records in total, with a 5-second server time limit per query and a 60-second wall budget. It never retries. If a budget runs out, that section and every later one report `collected: false` with the reason, and `collection.complete` is false; a partial cohort is never printed. It fails if output would contain a record identifier. Run it against a replica or off-peak, at most once per environment per day, and keep manifests and outputs outside the repository with the manifest checksum each report prints.
