# Measuring deterministic mapping and tracklist improvements

Draft, November 1, 2026. This is the measurement specification for merged PR32 and PR33, supporting the [AI hold in revision 7](AI_ASSISTED_MAPPING_PLAN.md#current-decision-and-measurement-plan--november-1-2026). It authorizes no implementation, database collection, deployment, provider/model calls, or trial changes. Start with available evidence; implement only the missing measurement contracts after a separately scoped build request. Operational commands remain in the [Last.fm runbook](LASTFM_SYNC.md#monitoring-and-verification).

## Questions and scope

- **PR32 — evidence coverage and ordered comparisons:** do moderators receive truthful warnings about bounded retrieval, failed hydration, retained stale candidates, and differing ordered recordings? Do those warnings and comparisons reduce active review effort or independently verified mistakes? Reporting more incomplete evidence can be an improvement in visibility; fewer warnings alone is not success.
- **PR33 — bounded catalog rediscovery:** when a matching catalog album becomes available, do eligible unresolved cases gain useful candidates without a manual refresh? How much delay comes from scanning, queueing, provider failures, or unsupported name matches? Does this happen without displacing normal sync work or overriding moderator decisions?
- **Downstream readiness:** after discovery and explicit mapping approval, which demanded albums still lack a usable reviewed baseline? This identifies the next deterministic bottleneck; it does not attribute all readiness changes to either PR.

The [November 1 metrics](QUEUE_METRICS_2026-11-01.md) are documented aggregates, not independently rerun queries. They report 42 production approvals outside empty candidate lists, including 38 where publication followed discovery, and 926 pending production baselines. They motivate these questions, not a claim that PR33 fixes all 42 or that 926 listeners are blocked. Raw report outputs and the follow-up query/results were not found during the earlier local review. The allowlisted sample, dev's single listener/moderator, selective approvals, retrospective candidates, and missing decision-time labels limit inference.

## Exposure and observation manifest

Maintain one versioned manifest per environment. Record study/schema version, source commit, collector version, actual backend/worker/frontend deployed revisions, activation/rollback timestamps in UTC, relevant flags, allowlist scope version, collection start/end, and evidence location/checksum. The CLI's `--environment` argument is a report label, not proof of the database selected by its connection; verify the named target separately without printing credentials.

Define `T32` from verified exposure to the PR32 API and moderator frontend together; record mixed-version observations separately. Define `T33` from a worker containing PR33 actually running with discovery enabled. Merge timestamps are not exposure timestamps. Flag-off periods and deployment changes are distinct strata, not silently discarded failures. If the two changes ship together, report their combined exposure and mechanism-specific outcomes; do not estimate separate causal effects from one before/after comparison.

Proposed operational defaults are **14-day intake windows and 7 days of follow-up per case**, with daily snapshots and a weekly readout. These bound effort; they are not sample-size calculations, service-level targets, or approved scheduled tasks. Confirm the windows and UTC snapshot time before collection, then freeze them. Baseline intake is `[T - 14 days, T)` and post-change intake is `[T, T + 14 days)` for the relevant exposure. Allow post-change follow-up through `T + 21 days`. Baseline cases whose follow-up crosses activation are mixed-exposure, not clean controls; if usable older evidence exists, use a baseline intake ending seven days before `T` instead and declare that choice before analysis. Otherwise report prospective post-change behavior only. Do not reconstruct historical evidence by calling providers today.

Use half-open intake intervals and a fixed analysis cutoff. Compare the same eligibility and follow-up rules within each environment. Do not sum overlapping rolling reports. Record provider outages, catalog growth, reviewer availability, allowlist changes, and concurrent product changes. November 1 is a descriptive snapshot until exposure and provenance establish otherwise.

## Units, cohorts, and clocks

Private internal joins use existing identifiers; exported reports contain aggregates only. No public MongoDB IDs or provider IDs are introduced as Rescened identities.

| Unit | Definition and separation |
| --- | --- |
| Mapping case | One global normalized provider/artist/title case. Multiple encounters, listeners, candidate albums, or retries do not make independent cases. `listenerCount` summed across cases is case-listener memberships, not unique people. |
| Eligible case/album pair | Case status is `pending` or `no_catalog_match`; artist and title satisfy the versioned PR33 matcher, including supported edition-label simplification and credited artists. Album exists in the public local catalog. Cohort enumeration must traverse bounded pages to their declared end, not apply a per-pass cap as a lifetime eligibility filter. `approved`/`rejected` cases are excluded at entry. |
| Fresh pair versus new availability | At eligibility time, classify whether a durable job for this pair already exists and whether this album is already a usable candidate. New-job and candidate-gain denominators include only the respective at-risk subsets. Existing/skipped/failed pair jobs are shown separately; PR33 does not reset them simply because a case reopens. |
| Historical backlog | Pairs already eligible at verified activation, or at the first verified cohort census if earlier eligibility is unknown. Start a backlog clock at that census; do not label it publication latency. Freeze the initial set and report subsequent exits. |
| Newly eligible pair | First eligibility occurs during intake, split into new catalog publication for an existing case and a new/reopened case against an existing album. Record which prerequisite arrived last; do not pool their latency distributions. Previously processed pairs retain their prior-job stratum. |
| Discovery attempt | One actual discovery execution, separate from job lease acquisitions, retries, and skips. Tie it to case revision, trigger, job/pair when present, and evidence version. Recommendation calls are a separate PR32 unit, grouped by target/revision. |
| Review episode | One target/revision and evidence snapshot presented for a decision, with retries/reopens linked locally. Repeated clicks or request retries do not multiply decisions. Mapping and baseline episodes remain separate. |

Use a recorded committed catalog-availability time when available. MongoDB ObjectId time, a preallocated `createdAt`, or scan/job creation is not a verified publication timestamp. Without a commit record, record the interval between the last verified absence and first observation; report bounds or observation-to-candidate latency with that label. Set pair eligibility time to the later of verified catalog availability and case eligibility. Do not impute exact clocks from daily snapshots.

Keep approved/rejected/deleted or otherwise ineligible exits in the original cohort as competing outcomes. They cannot disappear from the denominator. Cases without the full follow-up window are immature/censored, not failures. Unknown entry history is an explicitly unknown stratum, not inferred fresh eligibility. Deduplicate case-level gains across albums; report pair-level outcomes alongside them.

## Metric definitions

For every proportion print numerator, denominator, unit, window, exposure, and missing-data count; `0/0` is `null`, not zero. `H` is the frozen follow-up duration. `P_H` contains eligible pairs with no prior pair job and enough elapsed follow-up by cutoff; `G_H` is the subset whose matching album was not already a usable candidate at entry. Exits remain in these sets. A **usable candidate** here means the matching local catalog album appears in a newly persisted, provider-complete discovery result bound to its then-current catalog revision. It means available for moderator review, not correct or approved; record query/candidate caps and conflicts alongside it. A stricter no-cap/no-conflict subset is reported separately.

### PR33: availability and reliability

| Metric | Formula and interpretation |
| --- | --- |
| Enqueue reach by H | `count(p in P_H with durable pair job created by eligibility + H) / count(P_H)`. Include eligible pairs never enqueued. A job-only sample cannot estimate this rate. |
| Candidate gain by H | `count(p in G_H with first usable matching candidate by eligibility + H) / count(G_H)`. Also report distinct gaining cases / distinct cases represented in `G_H`, once per case. This is availability, not precision. |
| PR33-observed gain | Same denominator `G_H`, numerator restricted to gains first persisted by the matching catalog-triggered job with that album absent from its pre-run snapshot. Gains from manual refresh or other jobs are separate outcomes, not credited to PR33. If trigger/provenance is missing, attribution is unknown. |
| Pair outcome distribution at H | Partition `P_H` into: not enqueued; pending/running/retrying; executed successfully with matching candidate; executed successfully without matching candidate; terminal error; skipped because eligibility changed; other/unknown. Counts must sum to `count(P_H)`. Candidate gain is tracked independently because another job may already have supplied the candidate. |
| Terminal-error incidence | `count(p in P_H whose pair job is terminal with error at H) / count(P_H)`. Also show terminal-error jobs / all enqueued jobs in this cohort, clearly labeled as conditional. Retry attempts / unique enqueued jobs measures retry load, not an error probability. |
| Delay decomposition | Eligibility-to-enqueue, enqueue-to-first actual execution, and eligibility-to-first usable candidate. Print median/p90 and observed counts only for measured events, plus censored/exited/unknown counts and gain-by-H. Never describe successful-only latency as the experience of all cases. Separate publication clocks from observation/backlog clocks. |

Current `catalogRediscoveryJobs.completed` means `status: done` with no error. The worker can return without discovery when a case is missing or no longer eligible, so this count includes safe skips. It cannot establish successful retrieval, candidate gains, or the partition above. Existing `attempts` counts lease acquisitions; it is not a provider-call counter. Job `updatedAt` is not an immutable execution-outcome timestamp. See [worker execution](../lib/listening/worker.js), [job schema](../models/Listening.js), and [report](../scripts/listeningQueueReport.js).

### PR32: evidence and presentation

Keep mapping discovery and baseline recommendation results separate. Define `R` as all observed executions with the applicable exposure/version. Partition into fresh results with known coverage, retained/stale results, failures without results, and unknown/missing records. For baseline results, distinguish browse completeness, failed hydration, uninspected equally ranked competitors, ordered non-equivalence, and non-competing comparisons. For mappings, distinguish provider incompleteness from query/candidate caps; they are not the same field. Count each reason within `R`, explicitly allowing overlapping reasons rather than adding them into a total.

- **Coverage-data availability:** `runs with the required versioned coverage fields / all observed runs R`. Missing fields never mean complete evidence. If failed executions are unobserved, the denominator is unknown and only a captured-result description is possible.
- **Coverage problem rate:** `runs with a known named coverage problem / runs with known applicable coverage`; show unknown and failed runs separately. More detected problems after PR32 can be truthful reporting, not retrieval regression.
- **Warning fidelity:** in a fixed, independently annotated replay set, `presentations with every required warning and no unsupported completeness claim / all replay presentations`. Report missed-warning cases / cases requiring warnings, and spurious-warning cases / cases requiring none. Fixture expectations derive from captured coverage/evidence, not copied UI strings. Offline replay establishes behavior, not production warning exposure or human benefit.
- **Comparison fidelity:** `reviewed release pairs with correctly classified ordered equivalence and differences / all independently checked release pairs`; group results by target/family and include repeats, equal-length substitutions, disc changes, failed hydration, and skipped competitors. Missing data yields unknown, not equivalence. This validates correspondence reporting, not standard/deluxe identity.
- **Decision-time provenance rate:** `review episodes with immutable candidate order, coverage, target/source revisions, recommendation, selected result, and evidence hash / all decision episodes in scope`. Historical latest candidates cannot supply missing decision-time records. A manual selection different from a recommendation is disagreement, not automatically an error.

Use [recommender](../lib/baselines/musicBrainz.js), [ordered comparison](../lib/baselines/tracklistComparison.js), [baseline panel](../frontend/src/Components/Community/BaselineReviewPanel.jsx), and [mapping discovery](../lib/listening/discovery.js) as integration points. Baseline hydration completeness is relative to the implementation's ranked competing set; it is not proof all musically relevant releases were inspected. Loading another browse page is not hydration. Mapping cap signals may coexist with `incomplete: false`, since that flag controls retention after provider failures.

### Moderator effort and baseline readiness

For a prespecified sample of review episodes, use a moderator-controlled start/pause/resume/end timer or observed task timing; do not infer active time from tab-open duration. Sum active intervals per episode. Report total active minutes, median/p90 with sample counts, and `total active minutes / adjudicated decisions` as a workload measure with abandoned/unfinished work separately visible. Compare case-mix strata, not dev with prod. Record blinded independent adjudication as supported/unsupported/insufficient evidence: `unsupported decisions / adjudicable sampled decisions`, with insufficient-evidence and unreviewed counts outside that denominator. Capture disagreements before showing the existing recommendation where practical. Reviewer approval is not the truth label.

At each snapshot let `N` be distinct normalized names from unexpired evidence belonging to active connections, as in [listeningMetrics](../scripts/listeningMetrics.js). Let `C` be names with a current active mapping to an existing catalog revision and `B` the subset with a usable reviewed baseline. Existing formulas are `count(C)/count(N)` for mapping coverage, `count(B)/count(C)` for baseline readiness among covered names, and `count(C)-count(B)` for covered names without a baseline. Names are not people or albums.

For album-level prioritization, let `D` be distinct catalog albums reached by names in `C` at the snapshot. Join effective baseline status and readiness from [baseline service](../lib/baselines/service.js). Report each category divided by `count(D)`: ready pending (current, unexpired selected candidate); unprepared pending; reviewed; stale; deferred/revoked; and unknown/invalid joins. Categories must partition `D`; also report usable-baseline count / `count(D)` independently. Candidate-ready does not mean reviewed or fully sufficient evidence. Unmapped names `N - C` remain separate unresolved demand; never force their candidates into `D`.

For longitudinal outcomes freeze `D0` at intake and retain albums that lose demand, mappings, or catalog availability as explicit exits. Report transitions for `D0` separately from fresh daily demand snapshots. Readiness may change through moderators, enrichment, imports, or expiry; associate documented causes where possible and otherwise label unknown. Pending catalog baselines alone cannot estimate blocked people or expected automatic listens.

## Bounded collection and safeguards

Propose at most one snapshot package per environment per day during the 21-day observation/follow-up run, plus one weekly analysis. This is a plan, not a newly scheduled automation. Preserve start/end timestamps because existing multi-query reports are not atomic snapshots. Store sanitized aggregate outputs with checksums and the manifest; use explicit window boundaries for period summaries rather than summing daily rolling reports.

Before running, inspect the named target and query plans. Existing scripts read current collections without comprehensive pagination/runtime budgets; a `--days` argument does not bound every query. A proposed collector should use projected indexed pages (up to 500 records), at most 10,000 materialized records per run, per-query `maxTimeMS` of 5 seconds, and a 60-second wall budget, with one collector at a time per environment, no automatic retry, and no disk-spilling aggregation. These are conservative operational starting bounds to validate, not statistical thresholds or claims about existing scripts. An aggregate timeout is still possible even with small output; stop on resource pressure, cap exhaustion, inconsistent source revisions, or unknown target. Resume only using a versioned checkpoint/high-water boundary with declared snapshot skew; do not present a truncated/resumed cohort as complete. Do not rerun providers or change worker bounds to generate data.

Monitor sync lag, expired leases, throttled/provider-error jobs, scan progress, backlog age, and collector latency alongside candidate outcomes. PR33 currently bounds scans, outstanding jobs, staggering, and retries; reference the [runbook](LASTFM_SYNC.md#sync-and-resolution-behavior) rather than duplicating its controls. New measurement must preserve those limits, moderator revision fences, rejected/approved-case protection, catalog publication ownership, and private-data boundaries. A verified safety regression is a reason to investigate immediately, not wait for a sample-size target; rollback or remediation remains a separately authorized action.

## Interpretation and decisions

Always show cases, pairs, jobs, attempts, decisions, and independent reviewed families separately. They are correlated units, not interchangeable sample sizes. Report observed counts and missingness first. Use uncertainty intervals only with an explicit sampling model: family/case-clustered resampling for sufficiently many independent clusters, or descriptive results when too few exist. A finite observed cohort proportion is exact for that cohort; extrapolation to future users is uncertain. Zero harmful errors in a small selectively reviewed sample does not establish safety. Do not treat repeated aliases or dev/prod duplicates as independent confirmations.

After the first run classify each question as answered descriptively, inconclusive due to sample size, or unmeasurable due to missing provenance. Extend intake only through an explicit revised observation budget; never run indefinitely until the desired result appears. Set no arbitrary pass rate. Investigate unqueued eligible pairs, terminal failures, misleading warnings, or residual readiness blockers through concrete cases and fixtures. Prefer deterministic fixes when the remaining problem is retrieval, freshness, matching, evidence presentation, or preparation. Lower latency without quality and denominator checks is insufficient evidence of benefit; higher incompleteness reporting can be correct.

AI remains deferred. Reconsider only for recurring complete-evidence, public-input-eligible judgment cases with independently checked errors or material active effort after these improvements. Any future evaluation needs a defined family-separated dataset, comparison against the improved deterministic baseline, named model, and separately approved numeric budget. Expanding the allowlist merely triggers reassessment.

4. **Validate before collection.** Use captured fixtures for PR32 warnings/comparisons and PR33 capped scans, old IDs/late visibility, safe skips, revision conflicts, retries, restart/overlap, and eligible pairs beyond the first page. Add metric tests for duplicate pairs/attempts, gain from another trigger, existing candidates/jobs, immature follow-up, competing exits, missing clocks, and partition reconciliation. Run repository checks appropriate to touched surfaces; transaction changes require integration checks. No live-provider tests by default.
5. **Run the approved read-only observation and report.** Archive sanitized aggregates and manifest checksums, review weekly, then produce the fixed-window readout with censored cases and limits. No collection was performed by this draft. Separately authorize any instrumentation rollout or data-changing recovery; a failed job is not permission to refresh or reprocess it.
6. **Choose the next work from measured gaps.** Possible work includes residual title/artist matching, baseline preparation, warning fixes, or reducing scan/provider delay. These are contingent priorities, not findings that each feature is needed. Keep the family/edition migration and AI adapter/feedback/automation designs deferred behind their own gates.
